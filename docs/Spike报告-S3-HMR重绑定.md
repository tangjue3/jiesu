# Spike 报告 · S3 · HMR 后不丢选中

> 结论：**编辑循环已经连贯**。写回代码 → Vite HMR → React 重渲染 → 选中态自动恢复，
> 面板数值自动刷新，可以直接接着改下一个属性。
>
> 验证方式：真实 Chrome + 真实 Vite dev server + 真实文件写回，11 个用例全过。

---

## 1. S3 要解决的真问题

表面问题是"HMR 后覆盖层忘了选中哪个元素"。实测后发现它其实是**三个独立的失效**：

| 失效 | 现象 | 根因 |
|---|---|---|
| **A. 元素引用失效** | 面板高亮框消失，选中态指向已脱离文档的节点 | React 重渲染可能替换 DOM 节点 |
| **B. 源码行号漂移** | 下一次改动打错元素（或直接失败） | 写回改变了文件内容 → 后面所有元素的行号都变了 |
| **C. 属性值过期** | 面板显示旧值，改第二次必然失败 | `fromPx`/`fromBase` 是渲染时捕获的快照 |

B 和 C 是**正确性问题**，不只是体验问题。原实现把 `line:column` 缓存死，
写回一次之后定位信息就全错了。

## 2. 关键设计：双锚点交叉校验

行号会漂移，结构路径也会失效。**单独用任何一个都不安全**，所以两个都用。

```
data-jiesu-src="src/App.tsx:4:6"      ← 行号锚点：精确，但会漂移
data-jiesu-id="src/App.tsx#0.0"        ← 结构锚点：不漂移，但结构变了就失效
```

结构锚点是 **JSX 元素在 AST 里的层级索引链**：

```
<App>
  <div>          → 0
    <nav>        → 0.0
      <span>     → 0.0.0
```

只依赖元素之间的相对结构，**完全不依赖行号**。

### 定位决策表

| 情况 | 行为 |
|---|---|
| 行号锚点 == 结构锚点 | ✅ 直接命中（最可信） |
| 只有结构锚点（行号漂了） | ✅ 用结构锚点定位 |
| 两者冲突，且该行只有一个元素 | ✅ 采信行号（用户真移动了元素） |
| 两者冲突，且该行不唯一 | ❌ 明确拒绝：「元素位置已变化，请重新选择」 |
| 两者都没有 | ❌ 明确拒绝 |

**纪律：绝不猜。** 宁可让用户重新点一次，也不改错元素。

### 一致性保障

编译期注入的 id 与服务端定位用的路径，**必须由同一份算法产出**。
所以把 JSX 树遍历抽成了唯一实现 `src/core/locate/jsx-tree.ts`，
注入层和定位层都从它取数据——否则 id 与定位对不上，交叉校验形同虚设。

## 3. 客户端如何找回元素

选中时记下一组指纹，HMR 后按指纹找回：

| 优先级 | 指纹 | 强度 |
|---|---|---|
| 1 | `data-jiesu-id`（编译期注入） | 跨 HMR 完全稳定 |
| 2 | 结构锚点 | 与 id 同源，id 缺失时降级 |
| 3 | 元素自身文本 | 只在唯一匹配时采用 |

找不到就明说「该元素已不存在（代码可能已被重构），请重新选择」，
而不是留一个指向死节点的选中态。

## 4. HMR 时序：为什么必须"等"

实测确认的链路：

```
客户端提交改动
  → 服务端写文件
  → 客户端立刻收到 changeApplied 广播   ← 此时 DOM 还是旧的！
  → Vite 侦测到文件变化
  → Vite 编译并推送新模块
  → 浏览器重新执行模块
  → React 重渲染，DOM 更新
```

从写文件到 DOM 更新，**中间有几百毫秒**。

踩过的坑：第一版实现在收到 `changeApplied` 时就刷新面板，
结果显示的还是旧值——因为那时 HMR 根本没发生。

正确做法：**轮询等待变化**。

```
检测节点被替换 → 用指纹找回 → 恢复
检测 class 变了 → 刷新面板数值 → 恢复
都没变        → 继续等（递增延迟：60/120/250/400/700/1200ms）
超时          → 仍然同步一次
```

同时用 `MutationObserver` 兜底，捕获**用户手动改代码**触发的 HMR
（那种情况下服务端没有任何广播，只能靠 DOM 变化感知）。

## 5. 顺手挖出的三个真 bug

### 5.1 `parent` 语义混乱（重构暴露）

旧代码里 `located.parent` 在不同地方含义不一致，导致：
- 改文本时找不到元素的文本（`parent.children` ≠ 元素自己的 `children`）
- 重排子项时操作错了对象

重构时统一了语义：定位结果同时返回 `element`（开始标签）、`jsx`（元素本体）、
`parent`（真正的父元素）。三个 bug 一次性暴露并修掉。

### 5.2 `fromPx` 用的是过期快照

```ts
// 旧：渲染时捕获
const computed = classToPx(prop.base ?? '');   // 渲染那一刻的值
input.onchange = () => {
  const fromPx = computed;   // ← HMR 之后这个值已经过期了
}
```

改成在 `onchange` 时从**当前 DOM 的 class** 实时反推：

```ts
const fromPx = this.currentPxOf(prop.key);   // 提交这一刻的真实值
```

这直接对应"代码是唯一真实来源"这条原则——**面板的当前值永远来自代码，不来自缓存**。

### 5.3 `MutationObserver` 观察 `document.body` 会抛异常

客户端脚本注入在 `<head>`，执行时 `document.body` 还不存在。
改用 `document.body ?? document.documentElement`。

## 6. 验证覆盖

### 单元测试（6 个）

- 结构锚点在行号漂移后仍定位到同一元素
- 行号漂移后仍能正确写回，且只动目标那一行
- 结构与行号都变了 → 明确拒绝 / 改写时找不到目标类 → 拒绝
- 写回后返回新锚点，客户端据此重新定位
- **连续 20 次写回，选中态始终指向同一个元素**

### 端到端（真实 Chrome，5 个）

- 元素带上了稳定 id
- 选中元素 → 改数值 → HMR 后选中态仍在
- HMR 后属性面板的数值已刷新为新值（12px → 48px）
- 可以连续修改：第二次改动仍作用在同一元素上
- 用户在编辑器里改文件导致行号漂移 → 选中态仍在，改动仍落对元素

## 7. 顺带解决的一个测试隐患

S3 的 e2e 最初单独跑通过、全量跑失败。原因是它和 V0.1 的 e2e
**共用同一个 demo 目录和同一份 `App.tsx`**，两个测试互相污染对方的文件内容。

修法：给 S3 建独立的 demo 目录。**测试之间不应共享可变文件**——
这个约定后续所有 e2e 都要遵守。

---

## 8. 对产品定位的意义

这一轮把"确定性编辑"从**单次操作正确**推进到了**连续编辑正确**。

之前的 V0.1 只能做一次改动。真实用户的工作流是：

> 选中 → 改 → 看 → 再改 → 再看 → ……

如果每改一次就要重新点一次元素，这个产品就没有实用价值。
S3 证明这条链路是通的，而且**不需要引入任何"猜"的逻辑**——
全部靠可验证的锚点与明确的拒绝。

这正是"确定性优先"策略的兑现：
**宁可明确拒绝，也不猜着改。** 拒绝的成本是用户多点一次；
猜错的成本是用户信任崩塌。
