# Spike 报告 · S5 结构化编辑（插入 / 删除 / 复制节点）

> 执行时间：2026-10-26 ｜ 代码：`jiesu/src/core/write/structure.ts`、`jiesu/spikes/s5/`
> 结果：**内核 16/16、端到端 5/5 通过**，全量 172/172，`tsc` 零错误

## 1. 为什么先做这个

UI 参考 V2 拍板走"**画布即代码**"：从组件库拖一个按钮进画布，落地动作就是**往 `App.tsx` 插入一段真实 JSX**。

但在此之前，内核只会"改已有节点的属性"和"重排已有节点"，**从来没插入过新节点**。
而插入恰恰是最容易把定位体系打穿的操作——它同时改变行号和同级索引。

所以 A0 的第一个动作不是画 UI，而是回答一个问题：

> **插入一个节点之后，我们还能不能准确找到它、并且不误伤别的元素？**

## 2. 结论

**成立。** 四件事全部为真（真实 Chrome + 真实文件 + 真实 HMR）：

1. 插入只改源码里那一处，缩进跟邻居一致，其余字节不变；
2. HMR 之后新节点出现在 DOM 上，并带着 `data-jiesu-src` / `data-jiesu-id`；
3. 服务端回传的新锚点能选中这个新节点（点了面板就打开，指向正确源码位置）；
4. 删除能把它从页面和源码里一起拿掉，且不留空行。

## 3. 最重要的发现：结构锚点会因结构编辑而顺移

之前 S3 的结论是"行号会漂移、结构锚点不漂移"。**这句话只在非结构编辑下成立。**

实测（`spikes/s5/structure.test.ts`）：

```
插入前： <section> 是 main 的第 2 个子元素 → 锚点 0.1，第 5 行
插入后： 新按钮占走 0.1（第 5 行），<section> 被挤到 0.2（第 6 行）
```

于是出现一个**双锚点拦不住的危险场景**：

> 用旧定位（锚点 `0.1` + 第 5 行）去解析新文件，**两个锚点会一致地指向新插入的按钮**。
> 交叉校验此时给出的答案是"完全可信"，而它是错的。

这不是理论风险：插入后若用户立刻再改一次属性，就会改到刚插进来的元素上。

### 由此确定的产品/工程约束

**结构编辑必须串行化**：

1. 服务端必须回传"接下来该选中谁"——插入指向新节点、删除指向父节点（`payload.select`）；
2. 客户端在结构编辑之后必须**等 HMR 落地、从 DOM 重读锚点**，才允许下一次编辑；
3. 撤销不能用"邻近行"启发式——插入场景下它会把相邻行误当成被替换内容。
   已改为记录**精确的字符区间片段**（`StructureResult.edits`）。

## 4. 实现要点

| 问题 | 做法 |
|---|---|
| 缩进 | **从邻居推导**，不硬编码 2 空格。单行片段取目标元素的缩进，多行片段按公共缩进归一后重新加前缀 |
| 自闭合 `<Card />` | 展开成 `<Card>…</Card>`，并连 `/` 前的空白一起替换，避免产出 `<Card >` |
| 空容器 `<div></div>` | 撑成三行，内层缩进 = 容器缩进 + 文件惯用缩进单位 |
| 删除 | 独占一行时连换行一起删（不留空行）；与同级挤一行时只删本体并吃掉一侧空白 |
| 片段校验 | 必须是**单根** JSX；多根/非 JSX 明确拒绝并说出原因（"检测到 N 个并列根节点"） |
| 无法安全插入 | 元素与同级挤在同一行 → 拒绝，要求先拆行（**改不了就明说**） |
| 新节点定位 | 插入后重新解析，用"字符区间落在插入文本内"识别新元素，回传其结构锚点与行列 |

## 5. 限制（明确不做）

- 不支持"元素与同级挤在同一行"时插入（要求先拆成独占一行）；
- 不支持一次插入多个并列根节点（要求调用方自己包一层容器）；
- 组件模板目前由调用方提供字符串，**组件模板库还没建**；
- 还没有 Studio UI——端到端测试直接走 WebSocket，模拟 Studio 将来走的那条链路。

## 6. 对下一步的影响

A0 剩下的工作可以放心展开了：

- 脚手架生成真实项目（空白画布的落点）；
- 组件模板库（每张组件卡 = 一段可插入的 TSX）；
- Studio 壳与 `/studio` 入口；
- 客户端串行化：结构编辑后等 HMR + 刷新锚点再放行下一次编辑。
