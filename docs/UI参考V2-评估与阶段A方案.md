> 输入：`jiesu_ui_reference_v2.zip`（README + 7 张高保真参考图，2026-10-26）
> 原图与原文已归档到 [`reference/ui-v2/`](reference/ui-v2/)，本文引用的页面编号与其一致。
> 本文档回答 README 第 7 节要求的三件事：定位复述、架构与关键问题、阶段清单。
> **结论先行：视觉层可以直接照做；但"自由画布"与"代码是唯一真实来源"之间有一处硬冲突，必须先拍板，否则做完 7 页会发现两条产品线打架。**

## 1. 一句话定位复述（以及本文档要挑战的地方）

参考文档的定位是：**AI 生成真实代码 → 界塑打开并呈现真实页面 → 像操作画布一样改 → 安全同步回代码**，同时支持从空白画布新建。

我们已建成的内核正好是这句话中间那一环：**元素级定位 + 确定性写回 + 布局语义编辑 + HMR 后不丢选中 + 变更篮**（151 个用例）。

**但"从空白画布拖组件"和"改真实源码"不是同一个物种**，见第 4 节。这是本文档唯一要求用户拍板的事。

| 页 | 参考图要求 | 需要的内核能力 | 现状 |
|---|---|---|---|

| 02 画布工作台 | 选中、移动、缩放、图层树、属性面板 | 定位 ✅ / 图层 ✅ / 写回 ✅ / **插入删除元素 ❌** / **尺寸编辑 ❌** / **画布壳 ❌** | 🟡 内核有，壳没有 |
| 03 组件资源中心 | 组件库、搜索、拖入画布 | **组件清单（AST 扫描）❌** / **插入节点 ❌** | ❌ 全无 |
| 04 设计系统 | 主题色、字体、间距令牌 | **CSS / `@theme` 写入 ❌**（内核只写 className） | ❌ 新能力 |
| 05 响应式适配 | 1440/768/390 三画板、断点覆写 | 三 iframe ✅ / **跨实例选中同步 ❌** / 断点归属 🟡（族模型只到 `md:` 一层） | 🟡 半 |
| 06 AI 视觉精修 | 框选 + 自然语言 + 前后对比 | **AI 通道 ❌** / overlay ↔ studio 跨 iframe 协议 ❌ | ❌ 全无 |
| 07 代码同步与版本 | diff、文件影响、校验、回滚 | diff ✅（行级）/ **文件级 diff 视图 ❌** / **typecheck 集成 ❌** / git 状态 ❌ | 🟡 有一半 |

**结论：7 页里只有 02 和 07 的内核是现成的，其余五页要么缺新内核能力，要么纯新建。**
这不是坏消息——恰恰说明现有内核不是白做的；但也说明**这不是"再画几个页面"的活**。

## 3. 视觉规范评价：可以直接照做

这套规范是我见过比较少见的、**能被机器直接执行**的：

| 项 | 值 | 为什么重要 |
|---|---|---|
| 背景 / 面板 / 边框 | `#F7F9FC` / `#FFFFFF` / `#E8ECF3` | 有具体值，不用猜"浅色一点" |
| 主色 / 点缀 | `#5276F5` / `#A78BFA` `#64CDB4` | 点缀色明确"不能喧宾夺主"，防止 AI 到处撒渐变 |
| 圆角 / 主按钮高 | 12px / 40px | 全局统一，最容易做歪的两处 |
| 字体栈 | `Inter, PingFang SC, Microsoft YaHei, system-ui` | 跨 Mac/Win 回退明确 |
| 间距体系 | 8px 栅格（8/16/24/32） | 比"间距舒服点"有用一万倍 |
| 壳层尺寸 | 左导航 72px、顶栏 60px | 固定，防止每页自己发挥 |
| 字号阶梯 | 正文 13–14 / 标签 11–12 / 区块标题 16–18 / 页标题 26 | 有层级，不是"大一点" |

**唯一要补的是 Logo**：参考图要求"同一个几何六边形/折带式 Logo，用一个复用 SVG，不从各张 PNG 裁切"。我会手写一个 SVG 组件（不是从图里抠），保证任意尺寸清晰。

## 4. ⚠️ 唯一必须拍板的冲突：自由画布的落地方式

参考文档 02 页要求"**可平移缩放的无限画布 + 从组件库拖入元素**"，01 页要求"**创建空白画布**"。

这天然导向 Figma / Builder.io 的模型：**画布维护一份 JSON 文档，导出时生成代码**。
一旦这么做，我们验证了半个月的"改真实源码、diff 只动一行、不写绝对定位"就降级成次要路径，产品变成第二条赛道（和 v0、Builder 正面撞）。

### 两条路

| | A. 画布即代码（推荐） | B. 虚拟文档 + codegen |
|---|---|---|
| 空白画布 = | 在磁盘上**脚手架生成真实项目**（Vite+React+Tailwind+我们的插件），画布 iframe 跑的就是它 | 内存里的 JSON 文档 |
| 拖入组件 = | 往 `App.tsx` **插入一段真实 JSX** | 往 JSON 里加一个节点 |
| 改属性 = | 已有的确定性写回 | 改 JSON 字段 |
| 导出 = | **不存在"导出"**，代码一直在磁盘上、可 git diff、可继续用 AI Coding 工具开发 | 需要 codegen，且生成物和用户项目风格必然不一致 |
| 与现有内核 | **100% 复用**（只需补"插入/删除节点"） | 内核几乎用不上 |
| 风险 | 脚手架 + 每项目一个 dev server，工程量在服务端 | 看起来快，但做出的是另一个产品 |

**我的判断：走 A。** 理由不是"我们已经有内核所以要复用"，而是 B 路线必然产生"生成物 vs 用户手写代码"的两套风格，用户第一次导出就会弃用——这正是我们在调研里否掉 codegen 路线的原因。

代价说清楚：**组件库 = 代码模板库**（每张组件卡背后是一段可插入的 TSX），不是 JSON schema。这块工作量比看起来大。

## 5. 另一处要改参考图的地方：右侧面板的 X / Y

02 页右侧显示 `位置 X 240 / Y 358`、`尺寸 W 166 / H 44`，还能直接输入像素。**这是 Figma 模型，和我们的安全闸矛盾**：

- 用户输入 `X=240` → 若写成 `left:240px` → 元素脱离文档流 → 换个屏宽就崩 → 我们自己的 `auditLayoutSafety` 会拒绝。
- 用户拖到某位置 → 若按坐标落地 → 同上。

所以面板必须重新解释为**语义化位置**：

| 参考图字段 | 我们的实现 |
|---|---|
| X / Y（px） | **只读显示**（由布局反推），不可输入 |
| 位置编辑 | 父容器 + 同级顺序 + 对齐方式（`items-*` / `justify-*`） |
| W / H | 可写，但落在 `w-*` / `h-*` / `basis-*` / `col-span-*`，不是 px 坐标 |
| 响应式约束 | 断点覆写（`md:` 前缀），不是固定 px |

> 这条很重要：参考图的 X/Y 是设计工具惯性，照抄会直接把响应式做坏。而"拖到哪就在哪"这件事，我们 V0.4 已经用 `translate-*` 解决过（元素跟手，但代码里没有坐标）——同一个思路可以复用。

## 6. 架构：不推翻内核，加一层"工作室"

```
┌──────────────────────────────────────────────┐
│ Studio（新建，React 应用）                     │  7 页壳：首页/画布/组件/样式/适配/AI/代码
│   AppShell + 设计令牌 + 7 页路由                │
│   画布 = iframe(用户页面) × 1~3（按设备宽度）    │
└───────────────┬──────────────────────────────┘
                │ WebSocket（扩协议消息类型）
┌───────────────┴──────────────────────────────┐
│ 本地服务（已有 server，扩能力）                  │  项目模型 / 组件索引 / 令牌 / 变更历史 / 写回
│   session.ts（写回+撤销）· 新增 project / index │
└───────────────┬──────────────────────────────┘
                │ 文件系统（唯一真实来源）
┌───────────────┴──────────────────────────────┐
│ 用户项目（Vite + React + Tailwind）            │
└───────────────┬──────────────────────────────┘
                │ Vite 插件注入
        Overlay（已有，跑在 iframe 内的页面里）
```

**三条职责边界（决定这套架构能不能长大）**：

1. **Studio 不碰 DOM**：所有元素相关操作都发给 server，由 overlay 在页面内执行，server 回报结果。
2. **Overlay 不碰文件**：它只负责"点哪、选什么、预览成什么样"，写文件永远只发生在 server。
3. **Server 是唯一状态源**：选中态、变更历史、项目模型都在 server，Studio 只是它的视图。

这样做的直接好处：**05 页的三画板天然成立**——三个 iframe 各跑一个 overlay，server 广播同一份选中态，三个视图看到的是同一个元素。这也是现在唯一缺的能力（目前每个 overlay 各自独立选中）。

**形态**：先做**浏览器版 Studio**（`npx jiesu` 起 server + 打开 `localhost:PORT/studio`），零安装、跨平台。
桌面封装（Tauri/Electron）留到阶段 C 之后再评估——注意 Tauri 在 macOS 用 WKWebView 拿不到 CDP，但**我们不需要 CDP**（靠注入），所以这条路是通的，只是现在没必要先付代价。

## 7. 阶段计划（对参考文档 A→D 的两处修订）

### 修订 1：阶段 A 就让 02 和 07 接真实数据

参考文档要求阶段 A"用模拟数据做 7 页"。我建议改成：

- **01 / 03 / 04 / 05 / 06**：mock 数据，先把视觉与交互骨架做对；
- **02 画布 + 07 代码同步**：接**真实 server + 真实写回**（这块内核已经有了，接一下的成本远低于做完 7 页再返工）。

理由：阶段 A 结束时要能回答"这条路到底能不能用"，而不是"页面看起来像不像"。把最有价值的两个页面先通电，剩下五个页面随时可补。

### 修订 2：阶段 A 之前插一个 A0

| 阶段 | 内容 | 验收（可演示，不是"页面做完了"） |
|---|---|---|
| **A0**（新增，2–3 天） | 脚手架项目生成 + 插入/删除 JSX 节点 + 组件模板库雏形 + `/studio` 入口 | 命令行建一个空白项目 → 浏览器打开 studio → 拖一个按钮进画布 → `App.tsx` 里真的多了一行 JSX |
| **A**（3–5 天） | AppShell + 7 页 + 设计令牌 + 02/07 通电 | 七页导航不跳、字号色彩一致；02 拖拽/改属性写回真代码；07 看到真实文件 diff 并确认写入 |
| **B** | 画布真可用：缩放平移、对齐吸附、撤销重做、多选、快捷键、三断点同页 | 不写代码做一个完整响应式页面，重开可继续编辑 |
| **C** | 项目接入与回写成熟化 + 组件索引 + 设计令牌写入 + 安全边界 | 真实项目里改一个按钮 → 看到正确 diff → 确认后项目仍能跑 → 撤销可复原 |
| **D** | AI 视觉精修 | 框选区域 + 一句话 → 结构化提案 → 逐项接受 → 代码变更可审阅 |

**A0 是我加的，理由**：它是"自由画布"这条路线的可行性验证。如果在 A0 就发现"插入节点后 HMR + 选中态保持"不成立（很可能不成立，因为我们从没测过"新增节点"），那 7 页 UI 做得再漂亮也得返工。**先证伪，再装修。**

### 每阶段的验收纪律（沿用现有约定）

1. 每条验收标准都必须能**真实跑一遍**验证，不接受"看起来对"。
2. 新增内核能力必须带**纯 Node 单测**（像 S2/S4 那样），UI 才可信。
3. 改动内核后全量 151 个用例必须仍然全绿。

## 9. 我明确不建议做的事

1. **不要做"独立的设计文档 + 导出代码"**——那是另一个产品，且和"代码是唯一真实来源"直接矛盾。
2. **不要为了画布好看而允许绝对定位**——我们的安全闸存在的意义就是拦这个。
3. **不要在阶段 A 就接 AI**——AI 精修依赖"结构化变更提案"，而提案的数据结构要等 B 阶段的画布模型稳定。
4. **不要 7 页一次全做**。先 A0 + 02/07 通电，验证成立后再补齐其余五页。
